# Coding Agent品質ループ

品質チェックは作業完了条件です。`Build`、`Unit Test`、`clang-tidy`を順番に実行し、失敗時は直ちに終了せず原因を分類して修正します。

## 分類と対応

- 複雑条件: Guard Clause、意味のあるPredicateを検討する
- 深いネスト: cleanup順序と副作用を保って構造を見直す
- 関数肥大化: 責務が分かれる場合だけ分割する
- 引数過多: 内部関数だけ、意味のあるParameter Objectを検討する
- コメント不足: 周辺コードと仕様を読み、WHYと処理の流れが分かるコメントを書く
- その他clang-tidy: 既存規約と警告原因を確認する

修正後は必ず同じ3段階を再実行します。数値だけを下げるHelper、`check1`のような無意味な抽象化、Config/Context構造体の乱造、不要なrenameや大量コメントは禁止します。

## コメントの方針

`company-internal-comments`の警告にはFixItを適用せず、対象の制御目的、状態遷移理由、HW/タイミング制約、workaround、復旧理由などのWHYを記述します。さらに、初期化、入力検証、通常処理、復旧、終了など関数内の処理段階が読み手に伝わるよう、主要な分岐・ループ・状態遷移の前後関係を必要な箇所で説明します。コードの逐語説明や、`iを増やす`のようなWHATコメントは追加しません。既存コメントが対象直前にある場合は重複させません。

## 変更前後の確認

- 公開ヘッダ、関数シグネチャ、公開型、エラーコード、ABI、外部シンボルを変更しない
- 既存関数はclang-tidyのCognitive Complexity、関数サイズ、引数数、ネストの悪化を許さない
- 新規内部コードはCognitive Complexity 15、関数サイズ80行、引数数6、ネスト3を初期基準とする
- 不明なI/Fは外部I/Fとして扱い変更しない
- `NOLINT(company-internal-comments)`は根拠を確認した局所例外だけにする

## 入口

導入先プロジェクトの設定後は、`tools/check-quality.sh`をCoding AgentとCIの共通入口にします。未設定の環境変数がある場合は成功扱いにしません。
